# 1. SSH Protocol

## SSH = Secure Shell

SSH stands for **Secure Shell**.

### EL5 explanation

Imagine you are sitting in front of a computer in your house, but the Linux server you want to control is in another building.

SSH lets you safely open a terminal on that remote computer and work on it as if you were sitting in front of it.

SSH is a **protocol** for secure remote login and other secure network services over an untrusted network. It provides encryption, server authentication, integrity protection, and user authentication.

**Important correction:** SSH is a **protocol**, not just a command or an application.

---

# 2. What is SSH used for?

SSH is used to:

- Connect securely to a remote Linux/Unix server.
- Log in to a remote machine.
- Execute commands on a remote machine.
- Transfer files securely when using SSH-based file-transfer protocols/tools.
- Provide secure channels for other network services.

For example:

```text
Your Computer
     |
     |  SSH
     |  encrypted connection
     v
Remote Linux Server
```

The SSH protocol architecture includes:

1. **Transport Layer**
   - Provides server authentication.
   - Provides confidentiality/encryption.
   - Provides integrity protection.

2. **User Authentication**
   - Authenticates the user to the server.
   - Authentication can include passwords or public-key authentication.

3. **Connection Protocol**
   - Provides interactive sessions and remote command execution.
   - It can also support things such as port forwarding.

[Cross-checked against RFC 4251, RFC 4252, RFC 4253 and RFC 4254.]

# 3. SSH Port

The registered SSH service is associated with **port 22**.

```text
SSH     → 22
Telnet  → 23
```

However, **22 is the default, not a requirement**. An SSH server can be configured to listen on another port.

For example:

```bash
ssh -p 2222 username@server-ip
```

### Command explanation

- `ssh` → OpenSSH client used to connect to a remote machine.
- `-p` → specifies the port on which the SSH server is listening.
- `2222` → example SSH server port.
- `username` → user account on the remote server.
- `server-ip` → IP address or hostname of the remote server.

The SSH server (`sshd`) normally listens on port **22** unless configured otherwise.

[Cross-checked against OpenSSH/OpenBSD documentation and the IANA Service Name and Port Number Registry.]

# 4. SSH Clients

The notes divide SSH clients into two broad groups.

## A. Command-line / general SSH clients

The handwritten notes list:

1. **OpenSSH**
2. **PuTTY**
3. **Dropbear**

### 1. OpenSSH

OpenSSH is a widely used implementation of the SSH protocol.

On Linux, the `ssh` command is commonly provided by OpenSSH.

Example:

```bash
ssh username@server-ip
```

### Command explanation

- `ssh` → starts the OpenSSH SSH client.
- `username` → account you want to log in as on the remote machine.
- `@` → separates the username from the remote host.
- `server-ip` → IP address or hostname of the remote server.

Example:

```bash
ssh ec2-user@203.0.113.10
```

- `ec2-user` → example remote Linux username.
- `203.0.113.10` → example server IP address.

The general OpenSSH syntax is:

```text
ssh [options] [user@]hostname [command]
```

The OpenSSH client can also execute a command remotely:

```bash
ssh username@server-ip "hostname"
```

Here:

- `ssh` → SSH client.
- `username@server-ip` → remote login destination.
- `"hostname"` → command executed on the remote machine.

[Cross-checked against the current OpenBSD `ssh(1)` manual.]

---

### 2. PuTTY

**PuTTY** is a graphical SSH client commonly used on Windows.

It can be used to establish SSH sessions to remote servers.

PuTTY is a **client application**, whereas SSH is the **protocol**.

So:

```text
SSH     = protocol
PuTTY   = client/application that can use SSH
```

---

### 3. Dropbear

**Dropbear** is a lightweight SSH implementation designed especially for resource-constrained systems such as embedded devices.

It is therefore different from PuTTY:

```text
PuTTY      → SSH client/application
Dropbear   → lightweight SSH implementation
OpenSSH    → full-featured SSH implementation
```

# 6. SSH Protocol List in the Notes

The handwritten notes also contain:

```text
Telnet
Rlogin
SSH
```

These are/were remote-login protocols.

## Telnet

Telnet is an older remote terminal protocol.

It is **not considered secure for normal remote administration**, because it does not provide SSH-style encryption and authentication protection.

## Rlogin

Rlogin is an older Unix remote-login facility.

It predates SSH and does not provide the security protections expected from modern SSH connections.

## SSH

SSH was designed to provide secure remote login and secure network services over untrusted networks.

Therefore, for secure remote administration:

```text
Telnet / Rlogin
       ↓
old / insecure choices

SSH
↓
secure modern remote-login protocol
```

The RFC documentation explicitly describes SSH as a secure replacement for insecure remote-login mechanisms such as Telnet and rlogin.

[Cross-checked against RFC 4251 and RFC 6270.]

# 9. Windows → Windows

The notes say:

> Windows to Windows we use RDP.

### Corrected explanation

**RDP (Remote Desktop Protocol)** is a Microsoft remote-desktop protocol commonly used to access Windows graphical desktops remotely.

So, for traditional Windows GUI remote access:

```text
Windows → Windows
       → RDP
```

However, this does **not** mean SSH cannot be used between Windows systems. Modern Windows also supports OpenSSH, so Windows-to-Windows SSH is possible when an SSH server is installed/configured.

Therefore:

```text
Windows → Windows GUI desktop
        → commonly RDP

Windows → Windows command-line/SSH session
        → SSH is also possible
```

# 10. IP Address + Username + Authentication

The handwritten notes contain:

> Must — IP - username and password / key

The basic idea is that an SSH connection needs to know:

1. **Which server?**
   - IP address or hostname.

2. **Which user?**
   - Remote username.

3. **How to authenticate?**
   - Password, public/private key authentication, or another supported method.

Example:

```bash
ssh username@server-ip
```

With password authentication, SSH may ask for the user's password.

With public-key authentication, a private key may be used instead.

### Example using a private key

```bash
ssh -i ~/.ssh/mykey username@server-ip
```

### Command explanation

- `ssh` → OpenSSH client.
- `-i` → specifies the identity/private-key file to use.
- `~/.ssh/mykey` → example private-key file.
- `username` → remote account.
- `server-ip` → remote server address.

**Important:** A private key is not the same thing as a password.

# 11. Password Authentication vs Public-Key Authentication

SSH supports multiple authentication methods.

Two common methods are:

## Password authentication

```text
Username
   +
Password
```

The server verifies the password.

## Public-key authentication

```text
Client                         Server
Private key  → authentication ← Public key
```

The private key remains on the client.

The public key is configured on the server.

The private key should be protected and should **never be casually shared**.

Public-key authentication is commonly preferred for server administration because it avoids sending the user's password as the authentication secret and can provide stronger operational security when properly configured.

[Cross-checked against RFC 4252 and current SSH documentation.]

# 12. PPK File

The handwritten notes say:

> We need to have `.PPK` file to connect via PuTTY.

### Corrected explanation

A `.ppk` file is a **PuTTY Private Key** file format.

It is **not the SSH protocol**.

It is also incorrect to say:

```text
.PPK = PuTTY SSH client
```

The correct relationship is:

```text
PuTTY
  ↓
SSH client/application

.PPK
  ↓
PuTTY private-key file format
```

A PPK file stores a private key and the corresponding public-key information in PuTTY's key format.

PuTTYgen is used to generate/manage PuTTY private keys.

[Cross-checked against the PuTTY documentation for the PPK file format and PuTTYgen documentation.]

# 13. `.pem` File — Important Correction

The handwritten notes say:

> `.pem = SSH protocol`

This is **incorrect**.

`.pem` is **not an SSH protocol**.

PEM refers to a text-based encoding/container format historically used for various cryptographic objects, including some private keys and certificates.

OpenSSH can use private keys in different formats, including its newer native private-key format and older PEM-style formats.

So:

```text
.PPK
→ PuTTY private-key format

PEM
→ cryptographic text encoding/container format

SSH
→ network protocol
```

Do not memorize:

```text
.pem = SSH protocol
```

That is wrong.

---

# 14. PPK vs PEM

A simple way to remember:

| Item | Meaning |
|---|---|
| SSH | Secure remote-connection protocol |
| OpenSSH | SSH implementation/software |
| PuTTY | SSH client/application |
| PPK | PuTTY private-key file format |
| PEM | Cryptographic text encoding/container format |
| RDP | Microsoft's remote-desktop protocol |
| Telnet | Older remote-terminal protocol |
| Rlogin | Older Unix remote-login protocol |

# 15. Converting Keys for PuTTY

If you receive a private key in an OpenSSH-compatible format and need it in PuTTY's native format, **PuTTYgen** can import supported private-key formats and save the key as a `.ppk` file.

Conceptually:

```text
OpenSSH private key
        |
        | PuTTYgen
        v
      .PPK
        |
        v
      PuTTY
```

PuTTYgen can also export keys from PuTTY's format into supported OpenSSH formats.

[Cross-checked against PuTTYgen documentation.]

# 17. SFTP

**SFTP = SSH File Transfer Protocol**

SFTP provides file access, file transfer, and file-management functionality over an SSH connection.

Example concept:

```text
Windows
   |
   | WinSCP
   | SFTP over SSH
   v
Linux Server
```

WinSCP commonly uses SFTP for secure file transfer.

**Important correction:**

```text
SFTP ≠ FTP with a password added
```

SFTP is a separate protocol associated with SSH.

[Cross-checked against WinSCP SFTP documentation.]

---

# 18. SCP

**SCP = Secure Copy Protocol**

SCP is an older SSH-based file-copy mechanism.

It is commonly available on Unix-like systems through SSH software.

Modern WinSCP documentation generally recommends SFTP where possible rather than SCP.

So:

```text
SFTP
→ modern SSH-based file-transfer choice

SCP
→ older SSH-based file-copy mechanism
```

[Cross-checked against WinSCP documentation.]

# 19. WinSCP — Windows to Linux

The notes indicate:

The practical idea is:

```text
Windows
   |
   | WinSCP
   | SFTP / SCP
   v
```

You can use WinSCP to upload/download files between Windows and an SSH server.

WinSCP normally asks for information such as:

- Hostname/IP address
- Username
- Password or private key
- Protocol
- Port

For SFTP, the SSH server normally uses port 22 unless configured differently.
